# Protocol and Compatibility

`contract/source.json` pins one exact upstream Service revision and the corresponding OpenAPI, Thread stream schema and semantic owner documents. `npm run generate` produces the generated HTTP schema and static resource bindings; release review includes the source identity, snapshot diff and handwritten adapters. Types are structural compile-time contracts, not runtime validation of every Service response or arbitrary payload.

The SDK deliberately removes obsolete Service protocols: `/auth/context`, ambient workspace header, Run SSE, legacy notifications, the separate queued-submission collection and old Run creation/continuation commands. The new public boundary is explicit workspace-path HTTP, `Submitted` receipts, Thread inbox, Run items and Thread SSE. Breaking callers must migrate rather than rely on fake compatibility endpoints. Old local resources and streams do not give the SDK authority to reshape durable Service state.

Transport does not retry mutations. A dispatched command followed by network failure has an unknown outcome; reuse the same idempotency key when the Service supports replay, then read durable state. Reads use bounded retries; HTTP errors preserve code, status, details, request ID and `Retry-After` without retaining credentials. Abort and local close affect only client-side work. Network failures retain the Fetch implementation's error, not an unused SDK transport-error wrapper.

Validation gates include automatic dispatch checks for every pinned operation and successful status, changed-contract generation tests, transport and stream framing, generated resource request/receipt and semantic-helper tests, TypeScript negative contracts, packaged ESM/typings acceptance and installed-consumer tests. A separately managed disposable Service is necessary for live authentication, idempotent 201/200 replay, nullable queued Runs, tool waits, readback and Thread SSE. A real browser session test is separate from Node's simulated session-fetch tests and cannot be claimed from them. No SDK release follows from passing local tests alone.
