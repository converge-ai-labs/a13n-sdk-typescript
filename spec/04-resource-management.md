# Resource Management

The generated `resources` tree and `http` client both cover every pinned OpenAPI operation, including administration, auth, health probes, binary transfers and provider actions. An ordinary typed resource method exists for every route; raw HTTP is an escape hatch, not a coverage requirement. Existing managed conveniences remain additive and source-compatible. The SDK does not invent old command names or flatten organization-owned resources into workspace scope.

`workspace.agents`, `workspace.threads`, `workspace.sessions`, `workspace.assets`, `workspace.connections`, `workspace.environments`, `workspace.environmentTemplates`, `workspace.secrets`, `workspace.skills`, `workspace.subscriptions`, and `workspace.memories` bind the workspace path. `organization.models`, `organization.modelProviders`, `organization.webProviders`, `organization.environmentProviders`, and `organization.connectorProviders` bind the organization path. Collection `list`, `pages`, `items`, `create` and local `ref` reuse one transport; references support `get`, conditional `update` and explicitly named actions only where the Service implements the matching endpoint. For any specialized operation, use the complete `client.resources` tree with its generated body, query and response types.

Generated OpenAPI types preserve request/response shapes; there is no catch-all managed action method. References only expose supported operations (`PATCH` where available, `PUT` for secrets and provider `test` where available). Subscription creation returns `CreatedSubscription`, including the one-time signing secret, rather than the ordinary `Subscription` read shape. Paged responses retain `next_cursor`; callers can retain the response to inspect Service headers. Generated resource uploads accept Blob or byte streams with an explicit supported content type for binary paths and `{file: Blob}` for multipart uploads, without serializing bytes as JSON. Every declared retire/delete operation and content read has a generated resource binding. Downloads and raw SSE expose an unbuffered owned body; semantic Thread SSE remains a separate observation adapter. Cursor collections get lazy `pages` and `items` helpers that snapshot filters, preserve page response metadata, and reject repeated cursors. Non-cursor and specialized readback endpoints do not acquire invented pagination.

Authorization, ETags, idempotency and resource lifecycle are Service-owned. A local collection reference carries no authority, and local pagination exhaustion says nothing about another writer's mutations. Neither organizations nor workspaces derive scope from a token or a previous resource read.

## Memory

`workspace.memories` provides list/pages/items/create and local `ref`; a Memory supports get/update/delete. `organization.memoryProviders` supports list/pages/items/create/ref and provider get/update/test. Provider ownership remains Organization-scoped even when its configuration binds a Workspace.

Memory file content uses JSON text, not Asset binary transfer. `memory.files` supports list/pages/items/create/ref/move, with get/replace/delete on a file reference. File paths, including separators and Unicode, are encoded once. File writes use the file ETag; Memory metadata update/delete use the Memory ETag. `memory.revisions` supports list/pages/items, integer `ref(seq)` with get/restore, and `purge(path)`. Restore undoes that change by writing its previous content; restoring a creation removes the file. It permits an omitted ETag only when the file is absent and preserves nullable file state.

`memory.records` supports list/pages/items/create/search and ref(id).replace/delete. There is no item GET, PATCH or record ETag; search sends its query in a POST body. No uncertain write, including `write_unconfirmed`, is replayed. `thread.memories` supports a non-paginated list, conditional create, and ref(name).update/delete. All mount mutations require the Thread ETag and preserve its returned successor. New Thread/Fork inputs accept mounts, Agent configuration accepts default mounts, and Run views retain the frozen accepted mounts rather than later Thread changes.
