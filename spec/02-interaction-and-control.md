# Interaction and Control

`workspace = client.resources.workspaces.ref(workspaceId)` selects scope explicitly. `workspace.threads.create(NewThread, {idempotencyKey})` submits a new Thread; `thread.inbox.create(Message, {idempotencyKey})` submits to an existing Thread. Both accept the complete generated body, including mounts, options, MCP headers and explicit nulls. `textPayload(text)` builds `{content:[{type:"text",text}]}` for either call without network I/O or hiding body fields. The caller supplies a concrete Agent ID (an Agent key may resolve on reads, but the SDK does not silently look it up for a submission).

A successful submission is `Submitted {thread, entry, run}`. Its `entry` is always durable; `run` is a `RunView` only if a Run started immediately, otherwise `null`. Creation can return 201 and an idempotency replay 200, which remain visible through `ResourceResult.response`. Neither outcome is a promise that execution succeeded. On a lost acknowledgement, retry the same body and idempotency key or reconcile the durable Thread/entry; a new key may produce another entry. The SDK never retries mutations automatically.

`thread.inbox` lists and creates entries; `ref(id)` reads, updates and deletes an entry, and `order.replace` reorders entries at the Service's supported paths and version preconditions. An entry may be pending, assigned, incorporated or finished; receipt processing is not Run completion. The SDK does not create an independent queued-submission resource or synthesize a Run for a pending entry.

`workspace.runs.ref(runId)` targets exactly one Run for read, committed Items, interrupt, resume, fork and bounded `wait({timeoutMs})`. `wait` polls the same Run until a terminal or waiting state, or raises `WaitTimeoutError`; it does not follow a successor Run. The deadline covers authentication, in-flight requests, response bodies, read retries and poll delays. Caller cancellation preserves its reason; client close aborts even when a caller signal was supplied. The timeout is finite and between 0 and 2147483647 milliseconds; zero expires without dispatch. The optional `pollIntervalMs` is positive and finite, defaulting to 500. A timeout stops local waiting and never interrupts execution. Resume accepts explicit answer payload and idempotency key. Fork yields another `Submitted` receipt, not a mutation of the source Run. Thread/Run/session status and concurrency rules remain Service-owned; read the latest representation instead of inferring it from stream delivery.
