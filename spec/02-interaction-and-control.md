# Interaction and Control

`workspace.threads.create(NewThread, {idempotencyKey})` and `agent.start(payload, {idempotencyKey, body?})` submit a new Thread. `thread.inbox.submit(Message, {idempotencyKey})` and `thread.submit(payload, {idempotencyKey, body})` submit to an existing Thread. A string convenience payload becomes `{content:[{type:"text",text}]}`; all other fields preserve the wire body. The bound Agent ID and Thread path come from the local handle. The caller supplies a concrete Agent ID for `NewThread` and `Message` (a key selector may resolve on Agent reads, but the SDK does not silently look one up when starting).

A successful submission is `Submitted {thread, entry, run}`. Its `entry` is always durable; `run` is a `RunView` only if a Run started immediately, otherwise `null`. Creation can return 201 and an idempotency replay 200, which remain visible through `ResourceResult.response`. Neither outcome is a promise that execution succeeded. On a lost acknowledgement, retry the same body and idempotency key or reconcile the durable Thread/entry; a new key may produce another entry. The SDK never retries mutations automatically.

`thread.inbox` lists, reads, updates, reorders and removes entries at the Service's supported paths and version preconditions. An entry may be pending, assigned, incorporated or finished; receipt processing is not Run completion. The SDK does not create an independent queued-submission resource or synthesize a Run for a pending entry.

`workspace.runs.ref(runId)` targets exactly one Run for read, committed Items, interrupt, resume, fork and bounded `wait({timeoutMs})`. `wait` polls the same Run until a terminal or waiting state, or raises `WaitTimeoutError`; it does not follow a successor Run. Resume accepts explicit answer payload and idempotency key. Fork yields another `Submitted` receipt, not a mutation of the source Run. Thread/Run/session status and concurrency rules remain Service-owned; read the latest representation instead of inferring it from stream delivery.
