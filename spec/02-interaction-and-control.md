# Interaction and Control

`client.agents.ref(agentId)` binds an Agent **ID** locally. `start(input,{idempotencyKey,...})` submits a new Thread; `send(threadId,input,{idempotencyKey,...})` submits with that Agent to an existing Thread. Input accepts plain text or a full generated `MessagePayload`. Typed `StartOptions` exposes all NewThread fields except the bound Agent ID/payload, including optional `message_history: MessageHistory` for one-time imported native Pydantic AI model-message context; `SendOptions` exposes the corresponding Message fields and cannot reseed a Thread. The imported objects are Service-validated completed conversation context, not display Items, historical Service execution or a parallel SDK message model. Thread readback retains the submitted import. They preserve session grouping, revision selection, delivery, run overrides, environment/memory mounts, MCP headers and explicit null. No Client Session lifecycle or Agent ownership of a Thread is inferred. The low-level equivalents remain generated `threads.create` and `threads.ref(id).inbox.create`.

Native `options.configuration` accepts the generated `RunConfiguration-Input` independently of `options.overrides`. Omission, null and explicit objects are transmitted distinctly, including `{}`, `allowed_hosts:null`, `allowed_hosts:[]` and namespaced extension JSON with false, zero, empty or nested values. The SDK neither merges hidden defaults nor normalizes host rules. Service selects defaults for a new Run. When steering an active (accepted or running) Run, it retains the frozen snapshot without a replacement and rejects a different explicit snapshot with `run_configuration_immutable`. A waiting Run is sealed, not active. `next_run` can select a new snapshot; recovery, resume successors and inline/async children retain the accepted snapshot. Resume has no independent configuration replacement parameter. Host normalization, extension-consumer validation, outbound/TLS policy and conflict decisions remain upstream-owned.

Both high-level calls return one `Interaction`, not separate start/wait/stream workflows. It retains the original `{data,response}` `Submitted` receipt, bound Thread and Entry, and nullable **receipt** Run; it offers finite async iteration, `result()`, and `close()`. The Service may return HTTP 201 for creation or 200 for replay. A receipt's assigned Run is not proof that its Entry was incorporated. On unknown acknowledgement, preserve the key and body; the SDK never invents keys or retries mutations automatically.

`result()` polls the bound Entry until `consumed`, then its `assigned_run_id` identifies the **exact** Run to poll. Assigned input can revert to pending at a seal, so assigned alone is never treated as consumed. Entry `failed`/`withdrawn` raises `SubmissionDispositionError` with its snapshot and safe identifiers, not an unrelated Run outcome. Waiting input remains queued behind a Run requiring human action; no automatic approval or resume occurs. The result validates Entry/Thread/Run identities and returns `RunOutcome {run,status,output,pending,failure,snapshot}` for completed, waiting, failed or cancelled. The snapshot retains original HTTP metadata; structured output is not flattened to text. The same result promise is shared by iteration and result-only callers. A second invocation of `result()` does not start a second observer.

One deadline covers Entry and exact-Run reads, authentication, response bodies, read retries and poll delays. The default is 300,000 ms and a 500-ms interval; `timeoutMs` is finite within 0–2,147,483,647 and `pollIntervalMs` is positive and finite. Zero expires without dispatch. Caller AbortSignal, timeout, interaction close and client close cancel local observation without re-submitting, interrupting or rolling back execution. Breaking finite iteration closes owned stream and observation. A completed result remains readable after close; a pending one rejects without silent restart.

`client.runs.ref(runId)` targets one exact Run. `.wait(options)` returns the same `RunOutcome` projection for that Run and checks the returned ID on every read; it never follows a later successor. `.items()` reads committed display, `.interrupt()` is explicit remote mutation, and `.resume({approvals,calls,input?},{idempotencyKey})` submits a complete native pending-result batch with optional ordinary `MessagePayload` in one atomic request and creates a **distinct** Run handle. It does not send an extra inbox message or interpret `input` as a tool answer. Service owns pending ID coverage, question-response validation, asset authorization and native ordering. Generated resources retain all other Run verbs (including fork) and complete wire request shapes. Thread/Run/session concurrency and state remain Service-owned.
