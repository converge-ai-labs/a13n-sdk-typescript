# Interaction and Control

`client.agents.ref(agentId)` binds an Agent **ID** locally. `start(input, options?)` submits a new Thread; `send(threadId, input, options?)` submits with that Agent to an existing Thread. Input accepts plain text, an ordered array of strings/public parts, or a structural `MessagePayload`. Root-exported `text(value)`, `json(value)`, `url(value)` and `asset(id)` own native part discriminators; order, duplicates, null and arbitrary JSON are preserved. Public `StartOptions` exposes `sessionId`, `agentRevisionId`, `messageHistory`, delivery, memories, environments, `mcpHeaders` and grouped `options`; `SendOptions` cannot reseed a Thread. Nested contract fields retain native names. Public structural aliases `RunOptions`, `RunConfiguration`, `AgentOverride`, `MessageHistory`, mount/header types and pending/status/failure primitives expose every pinned selectable field without requiring generated-schema imports or creating a second schema hierarchy. No generic Agent output assertion is made.

Imported `messageHistory` is one-time Service-validated completed native Pydantic AI context, not display Items, historical execution or a parallel SDK message model. Thread readback retains the import as `message_history`. Service owns session grouping, revision selection and execution policy; no Client Session lifecycle or Agent ownership of a Thread is inferred. Low-level equivalents remain generated `threads.create` and `threads.ref(id).inbox.create` with full native wire shapes.

`options` has one native grouping: `{configuration, overrides, labels, max_usage}`. There are no duplicated flattened selectors. Configuration is distinct from Agent revision overrides. Omission, null and explicit objects are transmitted distinctly, including `{}`, `allowed_hosts:null`, `allowed_hosts:[]` and namespaced extension JSON with false, zero, empty or nested values. The SDK neither merges hidden defaults nor normalizes host rules. Service selects defaults for a new Run. Steering retains the accepted active Run's snapshot and rejects a different explicit snapshot with `run_configuration_immutable`. Waiting is sealed, not active. `next_run` can select a later snapshot; recovery, resume successors and child execution retain their accepted configuration. Resume accepts no replacement configuration parameter. Host normalization, extension validation and outbound/TLS policy remain upstream-owned.

High-level start/send return one finite `Interaction`. Its immutable identity records origin `submitted`, Thread/Entry IDs and the chosen idempotency key. Its optional original `{data,response}` receipt preserves creation (201) versus replay (200). `receiptRun` labels provisional receipt evidence; `interaction.run` is null until Entry **consumption** authoritatively binds the exact incorporating Run. Assignment can revert to pending and is not incorporation. `result()` polls that Entry, then only its `assigned_run_id`. Entry failed/withdrawn raises `SubmissionDispositionError` with the exact snapshot and safe IDs, not a failed or unrelated Run outcome. Waiting input stays queued; the SDK never approves, resumes or follows latest pointers automatically.

`RunOutcome` exposes the exact Run command handle, `runId`, `threadId`, status, full structured output, optional string-only `text`, `pendingApprovals`, `pendingCalls`, native pending/failure and explicitly named HTTP `snapshot`. Empty string, false, zero, null and empty containers are retained; `text` is undefined for every non-string output. The first reply requires no Items request or reducer. Completed/waiting/failed/cancelled remain distinct. The shared promise is authoritative independently of live preview.

`client.runs.ref(runId).observe(options?)` constructs the same exact-bound Interaction without I/O; `run.result(options?)` delegates result-only use to that core. The first exact read validates Run/Thread identity before exposing the authoritative Run handle. `client.threads.ref(threadId).entry(entryId).interaction(options?)` recovers the same Entry observation without I/O, mutation or fabricated receipt/key. Origins `exact_run`, `recovered_entry` and `resumed` preserve their known identities; they never fabricate an Entry. Resume retains its original Run receipt. The old authored `Run.wait()` call shape does not exist. Generated reads remain unchanged.

One observation deadline spans Entry, exact Run and SSE, including in-flight authentication/body reads, bounded read retries and poll delays. The default is 300,000 ms with a 500-ms poll interval; timeout is finite within 0–2,147,483,647 and interval is positive/finite. Zero expires without a read. Settings supplied at construction or the first result call fix one budget; repeating result/iteration cannot restart it. Later result calls with options reject. An absolute caller AbortSignal retains its prior mutation time. Fresh identity recovery is a new explicitly bounded observation, not a silent extension. Mutation cancellation/timeout is separate from local observation timeout.

Caller abort, interaction close and client close cancel local work, never remote execution. `close(): Promise<void>` joins owned reader and observer cleanup even when a public iterator is paused; completed results remain readable. Raw iterator break closes the Interaction; preview break/interruption leaves its explicit lifetime open (see [Observation](03-observation-and-data-access.md)). A closed pending observation cannot be restarted.

`run.resume(answers, options?)` accepts one public ID-to-answer map. `approve()`, `deny(reason?)`, `returned(value)` and `failed(message)` produce native values and partition into **both** wire maps in **one** POST. Returned requires an explicit value; null is a value. Denial preserves omitted/null/empty reason. Optional `options.input` accepts the same public input and is part of that atomic request, not an extra inbox message or a tool answer. Service alone validates complete atomic coverage and exact idle-last-waiting eligibility. The return is an Interaction for the distinct authoritative successor, supporting result-only, raw and preview consumption through the same core. Completed/failed/cancelled Runs continue via normal explicit Agent send, not resume or automatic retry. Generated Run verbs, including fork, retain their complete native shapes; the SDK does not invent an authored fork alias.

High-level start/send/resume may omit `idempotencyKey`; one browser-compatible `globalThis.crypto.randomUUID()` key is chosen before dispatch and exposed with identity. Explicit keys are unchanged; unavailable crypto fails before dispatch. No mutation retries occur. Durable callers persist their own key and identical logical body **before** sending. A generated key is not promised recoverable from a cancelled invocation that never returns. Attempted dispatch without reliable acknowledgement, including malformed accepted receipts, raises `SubmissionUnknownError` with chosen key, safe operation/known IDs and original cause, never payload/auth evidence. Pre-dispatch validation/auth/cancellation keeps its original error; a canonical Service rejection envelope (code, message, details and request ID) remains `ApiError`. A bare/noncanonical gateway status is unknown acknowledgement, retaining its native ApiError status and any body parsing/read cause; low-level resource errors remain ApiError. Native resources retain their existing errors and explicit required keys.

Service owns Thread/Run concurrency and state. `ThreadView.last_run_id` names the latest seal of any outcome; its nearest checkpoint supplies continuation history. Failed/cancelled seals pause automatic advancement without erasing history. The SDK neither chooses an earlier successful Run nor forks or resubmits automatically.
